NAMING CONVENTION (IMPORTANT FOR THE IMPLEMENTER)
-------------------------------------------------
Every character, stage, boss, and notable enemy carries TWO names:

  GAME NAME  — the shipping name (e.g. "Shiro Same")
  REF NAME   — the real anime/VTuber character it is modeled on, written in
               brackets like [REF: Gawr Gura — Hololive EN]

The REF name exists so that during early development nobody has to ask "wait,
which one is the shark again?" It tells you exactly what the animation, palette,
voice, and vibe should be copying. Put it in the data as a `ref` field, surface
it in the F3 debug overlay and in dev-build character select, and gate it behind
`DEV_MODE` so it never appears in a shipping build.

  DEV_MODE = true  ->  character select reads "Shiro Same  [Gawr Gura]"
  DEV_MODE = false ->  character select reads "Shiro Same"

Flip one constant and every ref name disappears from the UI. Keep the two fields
separate everywhere — never concatenate them into a single display string.

>>> THE ONE-TO-ONE RULE (do not break this) <<<
Every playable character maps to EXACTLY ONE real counterpart. Never a blend,
never "X's look with Y's moves." The `ref` field holds one name, not a list.

This is a design constraint, not bookkeeping. A character built from three
sources has no silhouette and no voice — you can't animate it, you can't write
barks for it, and a player can't recognise it. A character built from one source
writes itself: you already know how they stand, what they shout, and what their
ability should look like.

Practical consequence: if a move you want belongs to a DIFFERENT character from
the same series, you don't get it. That move is a reason to ADD that character
as their own roster slot, not a reason to graft it on. This is exactly what
happened between revisions of this document:
  - Yamikage is Sasuke, so he uses lightning, black flame, and Sharingan
    foresight. Shadow Clones and Substitution were withheld from him because
    they are Naruto's. Naruto then joined the roster as Uzu (★4) and inherited
    that exact withheld moveset. Nothing had to be rewritten — the rule had
    already kept the moves clean and unclaimed.
Two series now field two characters each (Naruto, Dragon Ball). That is FINE and
does not violate anything. The constraint is not "one character per series" —
it is:
  (a) each character's `ref` names exactly one person, and
  (b) no move, weapon, or signature effect appears on two characters.
Same-series pairs must be visibly and mechanically distinct: put them at the
same rarity, make them read as rivals or family, and give them opposite play
patterns. Yamikage is a slow inevitable damage-over-time character; Uzu is a
swarm-of-clones character. Sora charges a single enormous attack; Han wants to
be hit. If two same-series characters ever start feeling interchangeable, one of
them is wrong.

Stages and bosses follow the same rule; only the STAGE ITSELF may reference a
whole series rather than one character, since a location isn't a person.

(Practical note: shipping a game with the ref names visible, or with art/voice
copied 1:1, is a takedown waiting to happen. The dual-name setup means that's a
one-line decision later instead of a rename-everything refactor. Build with the
refs; ship with the game names.)

================================================================================
SECTION 0 — THE ONE-PARAGRAPH PITCH
================================================================================

You are building GACHA SURVIVORS: a top-down, single-stick, auto-attacking
roguelike "bullet heaven" where the player survives 15–25 minute runs against
escalating waves of anime-flavored monsters. Every playable character is a
distinct anime or VTuber archetype with THREE signature moves — a unique
auto-attack (fires automatically), a special ability (manual, on cooldown), and
an escape move (manual, short cooldown, grants i-frames) — all of which express
that character's personality. Between runs, players spend gacha currency earned
in-run to pull for new characters and signature relics from a rate-up banner
system with pity. Stages are pastiches of iconic anime locales, each with its own
mob table, hazard, modifier, and boss. During a run you level up by collecting XP
gems and pick from generic stat upgrades, plus rare character-flavored relics that
drop from chests and bosses and fundamentally change how a build plays.

The feel target: "Vampire Survivors x Honkai-style gacha x anime convention
energy." Loud, fast, screen-filling, extremely readable, and funny.

================================================================================
SECTION 1 — TECH STACK & HARD CONSTRAINTS
================================================================================

REQUIRED:
- HTML5 + Canvas 2D. Vanilla JavaScript (ES modules). No build step required —
  it must run by opening index.html (or via a trivial `npx serve`).
- Zero external runtime dependencies. No frameworks, no CDN links, no fonts
  fetched from the network. Everything self-contained and offline-playable.
- Fixed timestep simulation at 60Hz (accumulator pattern), rendering decoupled
  and interpolated. The game must NOT be frame-rate dependent.
- Target: 2,000+ simultaneous entities at a stable 60 FPS on a mid-range laptop.
- Persistence: localStorage, single JSON blob under key `gachaSurvivors.save.v1`,
  with a `schemaVersion` field and a migration function stub.
- Seedable RNG (mulberry32 or xorshift128). ALL randomness routes through it.
  Two RNG streams: `run` (seeded per run, so runs are reproducible for debugging)
  and `meta` (gacha pulls — seeded from a persisted counter so you cannot
  save-scum by reloading).
- DEV_MODE flag in `/src/core/config.js`, defaulting to `true` during
  development and readable from the URL (`?dev=0`). When true, every UI surface
  that shows a name (character select, codex, boss intro card, F3 overlay,
  results screen) ALSO shows the `ref` field in a dimmed bracket next to it.
  Implement this once, in a single `displayName(entity)` helper — never sprinkle
  `if (DEV_MODE)` through the UI code. One helper, one flag, one flip to ship.
    displayName(e) => DEV_MODE && e.ref ? `${e.name} [${e.ref}]` : e.name

PERFORMANCE RULES (non-negotiable — enforce these from day one, not as a retrofit):
- Object pooling for enemies, projectiles, XP gems, damage numbers, particles.
  Zero allocation in the hot loop. No `new` inside update().
- Spatial hash grid (cell size ~64px) for all collision broadphase. Never do
  O(n²) checks.
- XP gem merging: when gem count exceeds 400, merge nearby gems into higher-value
  gems. Same for gold.
- Off-screen enemies: cull rendering, cheapen updates (movement only, no AI
  targeting), and teleport enemies that drift more than 1.5 screens away to the
  far side of the arena.
- Damage numbers capped at 60 on screen, pooled, and aggregated (if the same
  enemy is hit 5 times in 200ms, stack into one number).
- Cap particles at 800; drop oldest first.
- Include an FPS/entity-count debug overlay toggled with F3.

INPUT:
- Keyboard: WASD/Arrows to move, SPACE = escape move, E or RMB = special,
  ESC = pause, F3 = debug, TAB = show detailed stats.
- Mouse: optional aim mode for aimed characters (default is auto-aim at nearest
  / most valuable target — see per-character targeting rules).
- Gamepad: left stick move, A/X = escape, B/Circle = special. Use the Gamepad API.
- Touch: virtual stick bottom-left, two ability buttons bottom-right. Layout must
  not overlap the HUD.

ART & AUDIO (placeholder-first, upgrade-later):
- Do NOT block on art. Every entity renders from a data-driven "visual" object:
  `{ shape: 'circle'|'capsule'|'diamond'|'star'|'sprite', color, outline, size,
     emoji?, sheet?, frames? }`.
- Ship with emoji + procedurally drawn shapes as the default look. Every entity
  must still be readable at a glance: enemies are cool-toned with a dark outline,
  player projectiles are bright and saturated, pickups pulse.
- Build a `SpriteAtlas` module with a documented drop-in path so real art can
  replace placeholders later without touching gameplay code.
- Audio: WebAudio synthesized SFX (square/saw blips for hits, noise burst for
  explosions, rising arpeggio for level-up). One music track slot per stage that
  gracefully no-ops if the file is missing. NEVER let a missing asset crash the
  game — all asset loads are try/catch with fallback.

CODE ARCHITECTURE:
  /index.html
  /src/main.js            — bootstrap, game loop, scene manager
  /src/core/              — rng.js, pool.js, spatialHash.js, input.js, audio.js,

  /src/render/            — camera.js, renderer.js, particles.js, damageNumbers.js,

================================================================================
SECTION 2 — CORE GAME LOOP
================================================================================

META LOOP:
  Hub ("The Studio") -> pick character -> pick stage -> RUN -> results screen
  (earn Star Fragments + Gold + XP) -> spend on gacha pulls & Shrine upgrades ->
  unlock harder stages -> repeat.

RUN LOOP (the 60 seconds that must feel great):
  Move -> auto-attack fires on its own -> enemies die -> XP gems drop -> gems get
  vacuumed in -> level up -> pause + choose 1 of 3 upgrades -> power spikes ->
  screen fills with more enemies -> use escape move to slip a pincer -> use
  special to clear a swarm -> chest drops -> take a relic -> build comes online ->
  survive the boss at the timer.

RUN STRUCTURE:
- Default run length: 20 minutes (stage-dependent, see SECTION 7).
- A boss spawns at the halfway mark and at the end. Surviving the final boss =
  VICTORY. Dying = run ends, but you KEEP all currency earned (never punish the
  player by voiding their run rewards — this is a roguelite, not a punishment box).
- At the run's hard time limit, if the player is still alive after the final boss
  dies, the stage ends in victory. If they somehow stall, THE DIRECTOR spawns
  (SECTION 8) — an unkillable sweeper that ends the run.
- Pausing is instant and free. Level-up choice screens pause the sim entirely.

================================================================================
SECTION 3 — PLAYER CONTROL & GAME FEEL
================================================================================

MOVEMENT:
- 8-directional, analog on stick. No acceleration ramp longer than 80ms — this
  genre lives on precise dodging. Base move speed 165 px/s (tunable per character).
- The player has a small hitbox (radius 9px) drawn smaller than the sprite. Be
  generous. Players should feel like they *earned* the dodge.
- No collision with enemies (you walk through them, taking contact damage on a
  per-enemy 0.5s tick). No enemy-on-enemy hard collision, but apply soft
  separation forces so hordes spread into readable blobs instead of one pixel-thin
  conga line.

DAMAGE & DEFENSE:
- Contact damage has a 0.5s per-enemy internal cooldown and a global 0.25s
  i-frame after ANY damage taken, with a white flash + 120ms hitstop-lite
  (slow the sim to 0.35x for 60ms — only on player damage, never on enemy death).
- Armor reduces flat damage: `final = max(1, incoming - armor)`.
- Dodge chance is a flat roll, capped at 60%, shows a "MISS" popup.

JUICE CHECKLIST (implement all of these — they are the difference between a
prototype and a game):
- Hit flash (enemy tints white for 60ms)
- Knockback on hit, scaled by damage, resisted by enemy weight
- Screen shake: tiny on special, medium on boss slam, big on nova ults. Have a
  shake INTENSITY setting, and a "reduce screen shake" accessibility toggle.
- Damage numbers: white normal, yellow crit (bigger + pops harder), purple DoT
- Death effects: small enemies pop into 4 particles; elites explode with a ring
- XP gem magnet arc: gems accelerate toward the player with easing, not linearly
- Level-up: freeze frame, radial flash, ascending chime, the 3 cards fly in
- Low HP: red vignette that pulses with a heartbeat SFX under 25% HP
- Kill streak counter that appears at 25+ kills in 3 seconds
- Every special ability has a distinct screen effect (color grade, ring, zoom)

CAMERA:
- Follows the player with a light deadzone (24px) and smooth lerp (0.15).
- Slight lookahead in the movement direction (up to 40px).
- Punch-out zoom (1.0 -> 1.06) over 0.4s when a special fires. Never zoom in
  during combat — readability wins over drama.

================================================================================
SECTION 4 — THE CHARACTER SYSTEM
================================================================================

Every playable character has EXACTLY four gameplay pillars:

  1. AUTO ATTACK — fires automatically, no input. This is 70% of the character's
     damage and the core of their identity. Must be visually unmistakable.
  2. SPECIAL ABILITY — manual, 12–30s cooldown. Big, loud, build-defining.
  3. ESCAPE MOVE — manual, 4–9s cooldown. Grants i-frames. Movement/defense.
     Every character MUST have one — it is the skill-expression button.
  4. PASSIVE — always-on trait that shapes which upgrades you want.

Plus: base stats, a personality (2–3 barks that pop as speech bubbles), and a
SIGNATURE RELIC (SECTION 11) that supercharges them but is usable by anyone.

  S1: base

  3. BEGINNER BANNER ("First Impressions") — 20% discount, one-time, 10 pulls,

    6★ : 0.8%
    5★ : 7.2%
    4★ : 32.0%
    3★ : 60.0%

PITY (implement exactly — this is the part players actually feel):
  - SOFT PITY for 5★+: starting at pull 51 without a 5★ or higher, the combined
    5★+ rate increases by +6% per pull. It will therefore always resolve by ~pull 62.
  - HARD PITY for 5★+: pull 70 guarantees a 5★ or higher.
  - HARD PITY for 6★ (rate-up banners only): pull 90 guarantees a 6★.
  - 50/50 RULE: when you win a 6★, it is 50% the featured character. If you LOSE

  - 10-PULL GUARANTEE: every 10-pull contains at least one 4★ or higher.

  - Display the pity counter openly in the UI ("58/70 to guaranteed ★5"). Hiding

================================================================================
SECTION 8 — WAVE SYSTEM & THE DIRECTOR
================================================================================

The wave system is a TIMELINE, not a state machine. Each stage has an ordered
list of wave events keyed by time. The WaveDirector reads the timeline every
second and spawns accordingly.

WAVE EVENT SCHEMA:
  {
    t: 180,                       // seconds into the run
    type: 'spawn',                // spawn | swarm | ring | elite | boss | event
    enemy: 'gacha_zombie',
    count: 40,
    pattern: 'edge_random',       // see patterns below
    duration: 20,                 // spread the spawns over N seconds (0 = burst)
    modifiers: { hpMult: 1.0, speedMult: 1.0, affix: null }
  }

SPAWN PATTERNS:
  edge_random    — from random points just off-screen (default)
  edge_side      — a wall of enemies from one screen edge (left/right/top/bottom)
  ring           — a full circle around the player at radius 700, closing in
  cluster        — a dense blob from one point (the "oh no" pattern)
  chase_line     — a long snaking line that follows the player's path
  ambush         — spawn directly near the player, ALWAYS with a 0.7s telegraph
  scatter_interior — spawn at random points inside the arena, not just edges

STANDARD 20-MINUTE DENSITY CURVE (tune per stage, but this is the shape):
  0:00–2:00   — 15–30 enemies on screen. Teaching. One mob type.
  2:00–5:00   — 40–70. Second mob type introduced. First ring wave at 3:30.
  5:00        — FIRST ELITE. Drops a chest.
  5:00–9:00   — 80–130. Three mob types mixing. Swarms every 45s.
  10:00       — MID-BOSS. Screen clears first (satisfying), then the boss.
  10:00–15:00 — 140–220. Elite packs. Two elites simultaneously at 13:00.
  15:00–19:00 — 250–400. This is the "screen is fully covered" phase the genre
                exists for. Player's build should be deleting hundreds/second.
  19:00       — brief calm (5 seconds of NOTHING — the silence before the boss).
  19:05       — FINAL BOSS.

SCALING FORMULAS:
  enemyHp(base, t)     = base * (1 + 0.115 * t_minutes) * difficultyMult
                         * stageMult
  enemyDamage(base, t) = base * (1 + 0.06 * t_minutes) * difficultyMult
  enemySpeed(base, t)  = base * (1 + 0.012 * t_minutes)  // capped at 1.5x
  xpValue(base, t)     = base * (1 + 0.09 * t_minutes)
  spawnRate(t)         = baseRate * (1 + 0.18 * t_minutes)

  Enemy HP must scale SLOWER than a good player's DPS growth. The fantasy is
  becoming overwhelmingly powerful. If minute 18 feels like minute 3, you have
  failed. Target: a well-built player kills a common mob in 1 hit by minute 12.

THE DIRECTOR (adaptive difficulty — subtle, never obvious):
  Track a `pressure` value = (enemies within 300px) + (recent damage taken * 3).
  - If pressure < 20 for 15 straight seconds: increase spawn rate by up to 25%
    and pull the next wave event forward.
  - If the player is below 25% HP: reduce spawn rate 15% for 10s and increase
    heart drop chance. Do not announce this. Never let it be detectable.
  - Never modify enemy stats. Only spawn rate and pickup luck. Players can feel
    stat cheating and they hate it.

THE REAPER / "SHOW'S OVER":
  If the player exceeds the stage's hard time limit (duration + 3 min), spawn
  THE STAGE MANAGER — an unkillable (999,999 HP) figure with a clipboard who
  walks toward the player at increasing speed and one-shots them. He says
  "That's a wrap." This is the genre-standard hard stop. He is also worth a
  hidden achievement if you survive 60 seconds while he chases you.

  clear 0.8–1.2s telegraphs on everything lethal, an intro card (name + epithet
  + a one-line quote), a death animation with slow-mo, and a guaranteed drop of
  1 relic + 1 chest + Star Fragments. Bosses do NOT get contact damage — they
  hurt you with attacks you can read and dodge. This is the difference between
  "hard" and "unfair."

  Boss telegraph color language (be consistent across the whole game):
    RED    = damage zone, will hurt you, get out
    YELLOW = charging/wind-up, an attack is coming from this direction
    BLUE   = safe zone / the one place you should stand
    WHITE  = unavoidable, use your escape move NOW

SECTION 10 — LEVELING & GENERIC UPGRADES

within `pickupRadius`, with a magnet arc.

  L1->2: 9, L5->6: 76, L10->11: 190, L20->21: 475, L40->41: 1180
Expect a good run to reach level 45–70.

SECTION 14 — BALANCE TARGETS (use these as tests, not vibes)
================================================================================

  - A 3★ character with no upgrades should kill a Tier-1 fodder enemy in 1–2
    hits at minute 0, and in 3–4 hits at minute 15 (before upgrades).
  - A well-built player at minute 15 should be doing 8,000–15,000 DPS.
  - Time-to-kill on a stage boss: 25–50 seconds for an average build.
  - A run should produce 15–25 level-ups.
  - The player should take damage roughly every 20–40 seconds in the mid-game.
    Never zero (boring), never constant (unfair).
  - A full 20-minute run should award 250–450 gold and 8–25 Star Fragments.
  - No single upgrade should be mandatory. If playtesting shows "Extra Shot" is
    picked 95% of the time, nerf it — homogeneous builds kill this genre.
  - Every character should have at least two viable build paths. Write them down
    in a comment next to the character data.

BUILD A BALANCE HARNESS: a headless mode (`?sim=1&char=rin&stage=2&seed=42`) that
runs the simulation at 100x speed with a scripted "average player" (moves away
from the densest enemy cluster, always picks the highest-damage upgrade, uses
abilities off cooldown) and prints DPS/level/death time to the console. Run it
across all characters x all stages to find outliers. This is not optional — you
cannot hand-balance 19 characters.

  SPECIAL CASE — KIRA (Light Yagami): his instant-kill timers ignore enemy HP
  entirely, so the standard DPS metric reports him as infinite. The harness must
  measure him on ENEMIES KILLED PER SECOND instead, and must separately verify
  that he is genuinely weak before minute 4. If he clears early waves at the
  same rate as anyone else, his write rate is too high.

      3-star reaches S5, further duplicates of it convert to UNIVERSAL Fan
      Letters at full value instead of dead character-specific currency. This
      does not fix the pull feel but it stops the excess from being worthless.
  Ship FIX C now. Pick A or B before the gacha is considered done.

SECTION 19 — TONE & WRITING GUIDE
================================================================================
The game is affectionate parody, never mean-spirited. It loves anime and VTuber
culture and is laughing WITH it. Characters are warm, silly, and confident.
Bosses are absurd but genuinely threatening. UI copy is short and punchy.
Death messages are encouraging, never mocking. Every character gets at least
one line that makes the player smile.

The single most important design rule in this document:
    THE PLAYER SHOULD FEEL LIKE THE PROTAGONIST OF THEIR OWN ANIME —
    outnumbered at first, unstoppable by the end, and always one dodge away
    from an incredible comeback.

Build that feeling first. Everything else is decoration.
